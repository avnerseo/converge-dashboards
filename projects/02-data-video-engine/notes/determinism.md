# Determinism — how it is enforced, and what it does not cover

The brief's worry: anything that reads a clock, a random seed or the network
mid-render makes the output unreproducible and undebuggable. That is right, and
the answer is not "be careful". It is a contract plus a harness that fails the
run when the contract is broken.

## The contract

`scene/scene.js` exposes exactly three things:

```js
SCENE.init(payload)   // build the DOM once, from data only
SCENE.duration        // total seconds
SCENE.seek(t)         // set every visual property as a pure function of t
```

`seek(t)` must be pure. Same `t`, same pixels — in any order, any number of
times. The capture loop is then just:

```python
for i in range(n_frames):
    page.evaluate("(t) => SCENE.seek(t)", i / fps)
    frame = page.screenshot(...)
```

Nothing in the render depends on how long the render took. A frame is defined by
its index, not by when it was grabbed. That is the whole idea: **the timeline is
data, not elapsed time.**

Consequences, all deliberate:

- No CSS `animation` or `transition`. `scene.css` kills both with `!important`,
  because they run off the compositor clock and would advance while the
  screenshot encoder is busy.
- No `requestAnimationFrame`, no timers.
- The date shown on screen is formatted from the payload string, never from
  `new Date()`.

## The enforcement

`scripts/capture.py` does not trust the above.

1. **Network is cut.** Every request that is not `file://` is aborted and
   recorded. The run fails if anything was blocked. A scene that pulls a font or
   a logo from a CDN would render differently the day that CDN is slow.
2. **Non-deterministic APIs are trapped.** An init script replaces `Date`,
   `Date.now`, `performance.now`, `Math.random`, `requestAnimationFrame`,
   `setTimeout`, `setInterval` and `fetch` with pinned-constant versions that
   record each use. The run fails and names what was touched. Nothing throws
   mid-render — a throw would just produce one broken frame instead of a clear
   error.
3. **Fonts are verified.** If Heebo is not loaded, the run fails rather than
   falling back to a host font.
4. **Every frame is hashed.** SHA-256 per frame plus a hash of the whole stream
   goes into the manifest, so two runs can be compared exactly, and a specific
   frame that changed can be found.

The `converge-*.manifest.json` next to each output carries all of it.

## Chromium flags

```
--force-color-profile=srgb    identical colour on any host
--font-render-hinting=none    hinting is platform-dependent
--disable-lcd-text            subpixel AA depends on the display
--disable-skia-runtime-opts   raster paths otherwise vary with CPU features
```

**`--deterministic-mode` is deliberately not used.** Despite the name it turns
on begin-frame-control, so the compositor only draws when a client explicitly
drives frames. Playwright's screenshot path does not, and every capture hangs
until it times out. Cost of finding that: about twenty minutes. Determinism here
comes from the `seek(t)` contract, not from a Chromium flag.

## What is guaranteed, and what is not

Guaranteed: same payload + same Chromium build + same ffmpeg build → same
frames and the same output bytes. Verified by `checks/determinism_check.py`,
which renders twice and diffs the frame hashes and the file hash.

Not guaranteed: bit-identical output across *different* Chromium builds. Text
rasterisation changes between versions — the pinned build
(`chromium_headless_shell-1194`) and a full `chromium-1194` already produce
measurably different PNG sizes for the same frame. So the honest claim is
reproducible against a pinned toolchain, and the build path is recorded in every
manifest. For a daily pipeline that is the useful guarantee: yesterday's video
can be regenerated byte-for-byte from yesterday's payload.
